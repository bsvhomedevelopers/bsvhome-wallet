## UI Components and Styles

Before adding or changing UI, read [UI Components](../docs/UI_COMPONENTS.md) and [UI Style Tokens](../docs/UI_STYLE_TOKENS.md), then inspect the listed owner and current callers. The [WowPay refactor checklist](../docs/WOWPAY_UI_REFACTOR.md) tracks the approved migration.

- Reuse an existing component first, extend its explicit style or state when needed, and create a component only when the existing owner cannot express the requirement. Do not copy a similar component into a second implementation.
- Keep presentation-only shared components in `Packages/Components`, domain-aware reusable components in `Packages/PrimitivesComponents`, and page-specific composition in its Feature. Shared views take display data and callbacks; they do not acquire services or decide wallet rules.
- Maintain the global component inventory in the same change whenever a reusable component is added, extended, renamed, merged, or removed. Include its concrete source, supported inputs/states, usage example or caller, applicable pages, and honest status. Planned entries are not callable APIs.
- Extract HTML variables and repeated visual values into the existing `Style` package before consuming them in pages. Reuse `Spacing`, `Sizing`, `Colors`, `TextStyle`, and `Font.app` where their semantics match; keep WowPay semantic additions in `Style`. Do not repeat shared color, font, spacing, radius, gradient, or shadow literals in views.
- Maintain the style inventory alongside token changes. Keep one source of truth for each semantic value; use role names where equal values may later differ. Page-specific geometry need not become a global token without a current consumer or boundary.
- Preserve localization, appearance preferences, accessibility, loading/error states, and existing business validation when applying a visual variant. Prototype demonstrations do not authorize fake balances, addresses, transaction success, or wallet creation.
- The approved WowPay migration permits a narrowly scoped exception to the shared no-comments rule: `TODO(WOWPAY-...)` at a deferred capability's action or owner, with a matching entry in the refactor checklist. Remove both when implemented. This exception does not permit explanatory comments elsewhere.

## Task Completion

Before finishing an iOS task:
1. Use [Quality Checks](../skills/quality-checks.md) to choose targeted vs full verification
2. Run at least one real verification command for the touched codepath
3. If generated files changed, or Core changed iOS-facing interfaces, build inputs, or app integration, run the required generation step and verify iOS still builds
4. Keep imports clean and remove dead code

`swift build` succeeding is not the same as the feature working. For UI changes, exercise the changed flow on a simulator or device when the flow is reachable. If verification is blocked by unrelated repo state, report the exact command and blocking failure instead of claiming the change was verified.
