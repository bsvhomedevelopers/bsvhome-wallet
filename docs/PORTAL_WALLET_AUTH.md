# Portal Wallet Authentication

## Ownership and scope

`core/bsv_home_core/src/services/portal` owns the WowPay Portal challenge, BSV signature login, secure session binding and authenticated requests. The [2026-11-15 Android alignment](WOWPAY_ANDROID_ALIGNMENT.md) uses it for ordinary Paymail and traditional multisig. Swap remains retained implementation without a visible product entry. Shared service changes may affect non-iOS consumers; their integration is unverified under the iOS-only scope.

The ordinary iOS Portal environment is `https://paymail.bsvhome.com/api/portal`. Retained platform/MPC uses a separate `WowPayPlatformOrigin` configuration with its original `https://api-dev.hj0252.com/v2/api/` environment. Hiding its entry points does not migrate or delete its state. Core requires HTTPS. iOS uses an isolated ephemeral `NativeProvider` session limited to the configured origin and path, with cookies and response caching disabled. It rejects redirects and uses the platform's normal TLS certificate validation.

The authentication service remains the sole owner of wallet-signature login and protected requests. `BsvHomePaymailService` uses the same session contract for protected configuration, bindings and challenges; see [Paymail](PAYMAIL.md). Bundle configuration injects the Portal origin and trusted Paymail public origins. `BsvHomePortalSwapService` retains pairs, quotes, orders and payment recovery without a visible entry in this product. See [Portal exchange](PORTAL_SWAP.md) for that retained contract.

## Identity and signing

The current wallet must have a valid BSV mainnet P2PKH account and local signing material. Watch-only wallets and missing BSV accounts return explicit errors. Challenge and login requests contain `chain`, `address`, `deviceId` and `deviceType`; login adds `challengeId` and `signature`. They do not send a token, `userId` or `walletId`.

The challenge's UTF-8 message is retained byte for byte. The aligned V1 protocol requires exactly seven lines with no trailing newline: login purpose, current address, nonce, UTC issuance, UTC expiration, device ID and device type. The challenge ID is `C` followed by 32 lowercase hexadecimal characters; the nonce is also 32 lowercase hexadecimal characters. Expiration must be in the future and exactly 300 seconds after issuance; issuance permits up to 60 seconds of clock skew. UTC timestamps use the same canonical Instant representation as the Android contract. iOS uses device type `4`. A five-line challenge cannot downgrade a V1 request. The retained explicit `/v2/api/portal` protocol continues to require its five-line message, raw UTC timestamp strings, maximum 900-second remaining expiry and five-second issuance skew; there is no runtime fallback between protocols.

Validation runs before unlocking and again after signing. `SignDigestType::BitcoinMessage` signs only BSV messages using the Bitcoin Signed Message prefix and CompactSize lengths, returning Base64 of the recoverable 65-byte compressed P2PKH signature. Signing uses the existing Keystore/password port, and the recovered signature address must match the current wallet account. WalletConnect rejects this Portal-specific digest type.

## Session lifecycle

The token remains inside Core, secure storage and the `Authorization` header, with no Bearer prefix. It is not returned to Swift or put in a URL. Ordinary bsvhome sessions use the `portal_bsvhome` Keychain namespace with `whenUnlockedThisDeviceOnly` accessibility. Historical `portal_v2`, platform and MPC records remain intact and separate. The stored envelope binds the token to its Portal environment, local wallet ID and BSV address. Changing the configured origin invalidates the old cached session and triggers normal authentication; the old token is never sent to the new origin. Swap recovery state retains its existing environment scope and is not implicitly migrated between origins. Login must return both `address` and `chain`, matching the requested default BSV address and `BSV`; token-only success responses are rejected. A returned RFC3339 expiry is respected. Historical deployment checks returned an empty string for `expiresAt`; empty, missing and `null` values mean no client expiry was provided, without an invented TTL. Other nonempty malformed dates are rejected. Protected requests still require server session validation.

Authenticated requests serialize on one service instance. Multisig and Paymail first reads authenticate directly and do not require Swap pairs. The retained `connect()` method still queries pairs and must not serve as the BSV product's authentication acceptance probe. HTTP 401, a recognized session-expiry code or `forceLogout` clears the session and permits at most one fresh challenge/login and one repeated read. Mutations retain their no-replay policy. Other API failures preserve their code/message and do not trigger an automatic signing loop. Storage and wallet-unlock errors propagate. A malformed, expired or differently bound cached session is discarded; secure-storage read errors are not treated as cache misses.

Malformed response envelopes or typed response data return `BsvHomePortalAuthError::InvalidResponse`. This is distinct from an invalid locally configured or cached authentication session and does not remove the stored token or trigger another challenge/login. App error presentation can therefore identify incompatible Portal data without suggesting that signing in again will repair it.

Wallet identity is checked at request, unlock, signing, login and persistence boundaries. Changed wallets cannot save or use the previous request's token; conditional cleanup removes only a session bound to that request's original identity. `cancel()` invalidates pending operations explicitly because cancelling a Swift task alone does not cancel the UniFFI Rust future. The app invokes it when the Swap tab or Paymail surface is left. A pending HTTP response may complete, but cancelled operations cannot proceed to a later unlock, signature, login or session save. An unlock prompt already presented by the existing password port cannot be dismissed by this Core service; its return is checked before continuing.

## Online transfer password

Phase 4 adds `BsvHomePortalTransferPasswordService` in the existing [Portal service](../core/bsv_home_core/src/services/portal/transfer_password.rs), with [typed requests/snapshot](../core/bsv_home_core/src/services/portal/transfer_password_model.rs) and [static errors](../core/bsv_home_core/src/services/portal/transfer_password_error.rs). It is an additional authorization step for online actions; it does not replace the keystore encryption password or existing iOS system authentication, and an unavailable online service never selects an offline verifier automatically. Core, the latest complete Native suite, final app build and final public-watch UI lifecycle have passed. The separately approved live password lifecycle also passed; the alignment record defines the phase gate and remaining resource-dependent checks.

Only these exact V1 POST targets are accepted under the configured ordinary Portal base:

| Target | JSON request | Result |
| --- | --- | --- |
| `/wallet-auth/transfer-password/status` | `address` | Object with boolean `configured`, wrapped locally with wallet ID, address and generation |
| `/wallet-auth/transfer-password/set` | `address`, `newPassword`, and `currentPassword` only when already configured | Successful object; returns a configured public snapshot |
| `/wallet-auth/transfer-password/verify` | `address`, `password` | Successful object; completes the current authorization attempt |

Initial setup omits `currentPassword`; it does not send JSON null. Confirmation is checked locally and never sent. Changed passwords require the current password. New passwords use 8–128 UTF-16 code units, matching Android's length semantics, reject blank-only values and require an exact confirmation. Existing-password verification accepts 1–128 UTF-16 code units so existing shorter credentials are not silently redefined by setup validation. HTTP success also requires the successful response envelope and object-shaped data; status requires a real JSON boolean. The exact three V1 password POST targets accept string or integer success codes without imposing a particular code value, including numeric codes. This narrow compatibility does not change other V1 operations or the retained V2 `OK` requirement, and never overrides HTTP failure, `success: false`, `forceLogout` or invalid data shape.

The service requires current-wallet scope and rejects fixed-identity multisig auth services and the retained `/v2/api/portal` environment. The supplied wallet ID and the stored current wallet's main BSV address are checked before and after asynchronous boundaries. An HD receive-address selection does not change this account or the Portal identity. Public snapshots contain only wallet ID, stable address, configured status and auth generation; they are not passwords or authorization credentials. Caller-edited snapshot fields are rejected: set/verify requires equality with the service's last accepted snapshot and an unchanged generation, and queued operations recheck after acquiring their operation/auth locks. A service remains bound to its original identity even if the same wallet ID is later stored with a different address.

Requests reuse the scoped wallet-auth channel and raw `Authorization` token. Status may obtain one fresh authentication and repeat its read once after session rejection. Set and verify use `SessionRetry::Never`: a rejected session is cleared, but the mutation or password attempt is not automatically replayed. There is no password in URLs, public Paymail requests, persistent settings or logs. Core wraps password and confirmation inputs in zeroizing buffers; the native form clears its input properties before awaited submission and on cancellation. This does not claim that every Swift/FFI/transport string copy can be immediately erased from physical memory.

`cancel()` is permanent for a password service instance and advances the underlying auth generation. Late responses and queued old snapshots cannot authorize or publish a new result; reopening creates a new instance. `BsvHomeTransferPasswordError` carries static typed cases instead of backend messages or credentials. Its `requiresStatusReload()` receiver returns true for `Unavailable`, `InvalidResponse`, `InvalidSnapshot` and `NotConfigured`: the native owner drops the old status and offers a status reload before another submission. Incorrect-password, validation and rate-limit presentation retain their explicit typed behavior; none triggers an automatic password replay. Typed cancellation ends the prompt rather than offering an unusable retry on a cancelled instance.

The native `TransferPasswordViewModel` owns its loading and submission tasks. Scene `onAppear` starts status only from `.noData`; repeated appearance does not restart the load, and a status error uses the explicit reload action. The scene does not cancel on transient `onDisappear` or delegate loading lifetime to a SwiftUI `.task`. Both status and submit check revision, finished outcome and task cancellation at the first task poll before calling the service and after awaited work, including error handling. Its typed `Outcome` separates pending, completed and cancelled actions. Typed cancellation dismisses management as well as authorization, while background cancellation, screen-recording protection and privacy-sensitive presentation remain in place.

The confirmation authorization port and execution scope are owned by Core; the iOS [Transfer UI](UI_COMPONENTS.md#transfer-password-authorization) supplies the password presentation callback. Successful setup/verification resumes only that request. Core still rechecks wallet/account and review generation before signing and final broadcast. Settings management dismissal/replacement synchronously cancels and clears the model only if the binding's captured `presentedId` still matches. Authorization dismissal uses its captured `requestId` to cancel/clear that presentation and resolve its continuation once. These identities also reject delayed callbacks from an older prompt without cancelling a newer one. ## Multisig Client — 2026-10-14

`BsvHomeBsvMultisigService` composes the existing wallet-auth owner through a crate-internal typed multisig request target. It does not export token or arbitrary-URL capabilities to Swift. The first multisig request authenticates directly without a swaps/pairs prerequisite. Read requests may obtain one fresh challenge after session rejection; every multisig POST clears rejected sessions and returns its error without automatic replay.

Portal response parsing accepts envelope and bare error bodies, including HTTP 200 business failures and optional forceLogout. LOGIN_REQUIRED requires fresh authentication. Successful results require both HTTP 2xx and success=true. Frozen wallet identity and workflow version are rechecked around asynchronous authentication, requests and persistence. See [the current multisig contract](BSV_MULTISIG_PLAN.md) for permissions, independent transaction validation and funding recovery.

Multisig HTTP 429 responses, including custom error codes, and known rate-limit business codes start a 60-second monotonic cooldown in PortalClient. The request channel checks it inside the serialized connection boundary before cached-session work or login, so queued reads cannot trigger authentication during backoff. A rejected token is cleared when required, but a rate-limited request is never automatically authenticated or replayed. Paymail and Swap retain their existing request behavior.
