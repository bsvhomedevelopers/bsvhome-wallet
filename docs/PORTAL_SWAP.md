# WowPay Portal Exchange

## Ownership and scope

`core/bsv_home_core/src/services/portal` owns the Portal HTTP contract, exact asset identities, amount conversion, wallet and address binding, quote expiry, order idempotency, persisted recovery and payout verification. It uses the existing [wallet-signature authentication](PORTAL_WALLET_AUTH.md). iOS's `WowPayPortalSwapViewModel` renders that service and manages view activity, input debounce and query cancellation. The app resolver provides Core services, GRDB storage and Keychain storage. WalletTab's `PortalSwapPaymentPresenter` and `PortalSwapPaymentContext` own the shared native payment preparation and confirmation lifecycle; app navigation owns where the native confirmation is hosted. `MainTabView` hosts it for Tab and asset-detail exchange; the TRX acquisition sheet hosts its own instance above the original transfer confirmation. Shared Core behavior can affect other clients; non-iOS integration is unverified in this scope.

The Portal asset contract enables native BSV (8 decimals), native TRX on TRON (6 decimals), and TRON TRC20 USDT at `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t` (6 decimals). Asset identity is the exact chain, asset type and contract, rather than a currency code or symbol alone. The pair response must also match the expected symbol and scale; a network display label does not override asset identity. MNEE remains an unavailable placeholder. The generic DEX swapper retains its existing chain capabilities.

| Asset | Wire chain | Wire kind | Wire contract | Symbol | Scale |
|-------|------------|-----------------|---------------|--------|-------|
| Native BSV | `BSV` | `NATIVE` | Empty | `BSV` | 8 |
| Native TRX | `TRON` | `NATIVE` | Empty | `TRX` | 6 |
| TRON USDT | `TRON` | `TOKEN` | `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t` | `USDT` | 6 |

The documented ordered pairs are BSV → USDT, USDT → BSV, USDT → TRX and TRX → USDT. New capabilities, quotes and order submissions reject BSV ↔ TRX and same-asset pairs. Core intersects this allowlist with validated pairs returned by Portal; incorrect symbols or scales for recognized assets and missing provider metadata remain errors rather than disappearing as unsupported pairs. Source and destination must be resolved together because TRX and USDT share a chain but are different assets. Persisted `BsvHomePortalSwapDirection` retains all six serialized variants so historical orders and saved operations remain decodable. A known order retains its recovery path; an ambiguous operation for an unsupported direction retains its original operation ID but cannot submit a new create request.

The main Swap tab and the asset-detail exchange page are independent page containers with their own view-model state; both render the complete `WowPaySwapContentView` with amount entry, quotes, asset selection, orders and actions. Source selection shows only assets with an outgoing supported pair, in BSV/TRX/USDT display order. Destination selection shows only supported targets for the current source. MNEE is hidden from exchange selectors and shortcuts. Changing the source preserves a valid destination, otherwise selects a supported destination with USDT preferred. Reversal requires the reverse pair to be returned by Portal, and quick-pair cards require their displayed direction. Entry, retry and foreground refresh capabilities; loading, failure or an empty response clears quotes and blocks new requests. Removing a selected capability preserves the visible selection with unavailable feedback until the user selects a supported pair. Tapping Swap in an asset detail pushes the exchange page on the wallet navigation stack, hides the bottom tab bar and shows a back button to that asset detail. A fresh page and model are created on each entry. The existing `for_asset` entry default stays limited to BSV → USDT for BSV and USDT → BSV for the exact TRON USDT asset; this extension does not add a TRX asset-detail entry. An unsupported entry asset shows a localized notice, and the default BSV → USDT requires the same live capability check.

The iOS Home exchange entry uses the current total-assets card selection as its source asset. Each Home tap is consumed once; direct visits to the bottom Swap tab retain the user's current pair. BSV and TRX select USDT when their existing destination is unavailable, while USDT preserves a supported destination or selects the first supported target. The selection uses the validated capability list, waits for loading or refresh to finish, and keeps the selected source visible without quoting when no outgoing pair is available. A new Home entry clears the previous amount, selected order and quote; obsolete quote responses cannot replace the new selection. This Home entry does not change the Core asset-detail `for_asset` contract.

The iOS native mainnet TRX balance and network-fee acquisition actions open a large exchange sheet directly from the insufficiency notice, bypassing the generic acquisition menu and DEX page. The sheet reuses the complete Portal exchange content with independent state, starts with empty USDT → TRX input, and fixes the destination to exact native mainnet TRX. Source choices and quote/order requests use the validated pairs that pay out TRX; target changes, reversal and unrelated shortcuts are unavailable. Other assets and Shasta keep their existing acquisition flows. Existing non-TRX orders remain visible but cannot be paid from this sheet. Pending-operation recovery remains available in the normal Swap tab because the current pending-operation API does not identify its payout asset before retry; the acquisition sheet neither retries an unverified pending direction nor discards that operation. The sheet owns its native payment confirmation locally, validates the current wallet at every asynchronous preparation boundary, and cancels preparation or confirmation on dismissal, wallet change or backgrounding. Its payment confirmation displays subsequent balance or network-fee failures inline, without a second insufficiency or acquisition sheet. Closing the exchange sheet reloads the original transfer balance and fee, preserves its amount/recipient and requires another explicit confirmation; the refresh does not automatically reopen the insufficiency notice or submit the transfer. A broadcast deposit is not proof that TRX has arrived. USDT deposit payment still requires genuine TRON resource and fee availability.

## Quotes and orders

Portal supports floating-rate, fixed-input quotes. Core converts the normalized decimal input to exact unsigned minor units using the source asset's scale, validates returned pair/amount/provider/expiry, and formats display values from integer amounts. The quote request binds `fromChain`/`fromKind`/`fromContract` and `toChain`/`toKind`/`toContract` to the selected ordered pair, with empty contract strings for native assets. UI `selection.from` identifies the payment source and `selection.to` identifies the payout destination. Reversing a pair reverses these roles and uses the new source scale. Minimum and maximum amounts come from the returned quote. For compatibility with the deployed API, an absent, `null` or exactly empty-string `maxFromAmount` means no upper limit. Every nonempty maximum must still be a positive integer in source minor units; whitespace, zero, negative and decimal values remain invalid. Required amounts, lower limits, asset identity, provider and expiry checks remain strict. The UI debounces input, discards obsolete responses, clears quotes when the direction changes and prevents creating an order from an expired quote. Estimates are labelled as estimates; missing quotes and provider failures are never replaced by invented prices or amounts.

The recipient is the current wallet's destination-chain account and the refund address is its source-chain account. For USDT ↔ TRX, both roles use the wallet's TRON account, while the source and payout asset identities remain distinct. Missing accounts require adding the corresponding network account. A source key is never reused to infer the other chain's address. Portal session authentication and persisted scope retain the current wallet's BSV identity even when TRX is the source or destination. Before creating an order, Core checks the actual source asset balance: native TRX uses the coin balance and USDT uses the exact token balance. TRON resource and fee availability use the existing chain provider. This precheck does not establish that the source amount plus the exact fee is spendable; exact network fees require the returned deposit address and are calculated in the native payment confirmation. Both exchange pages explicitly explain this timing and do not display a fabricated fee.

Before the create request, Core saves a UUID `clientOperationId`, the quote and the exact addresses to the scoped `portal_swap_states` GRDB record. An ambiguous result keeps the original operation for retry. A recovered operation retains its original key even if the repeated request reports an expired quote; that response cannot retroactively establish what happened during the first ambiguous attempt. The same quote, addresses and key are reused; explicit definitive request errors can clear it. An order is saved before signing is offered. Cached order copies are explicitly marked stale and cannot be paid until refreshed. Scope includes Portal environment, wallet ID and BSV identity. Persistence failures propagate and block the next irreversible step. The order list decoder accepts both numeric and numeric-string totals, as the deployed empty-list response uses `"0"`.

For deployed order responses, an absent, `null` or exactly empty-string `actualToAmount`, `depositExpiresAt`, `sourceTxid`, `payoutTxid` or `refundTxid` means that value has not been provided. The order DTO converts these optional empty values before order merging or payment-report recovery. Nonempty values retain their existing amount, RFC3339 date and transaction-hash validation; required fields and native-asset contract strings keep their original contract. An absent remote source transaction never removes a locally recorded payment or enables another payment. An absent deposit expiry preserves the existing optional-expiry semantics without inventing a deadline.

Invalid response envelopes or DTOs produce a response-format error rather than an authentication-session error, and do not trigger session removal or another login. The iOS order list preserves cached records on failure, provides a retry action, and shows an empty-state message only after a successful empty result. Refreshing the list also rereads pending-operation availability so a recovered order does not leave an obsolete recovery entry visible.

## Payment and recovery

`preparePayment` assembles the order, exact transfer, payment summary and order-bound checkpoint with one fresh order query. Each order must be freshly validated as payable, match its original ordered pair/amount/addresses, have no incompatible action or verification requirement, and satisfy any provided deposit expiry. Unsupported memos fail closed. Payment is an ordinary fixed-amount transfer to the deposit address, with network fees separate, no token approval and `use_max_amount = false` for every source asset. Native TRX requires a native transfer with scale 6; USDT requires the exact TRC20 asset. The native confirmation includes the actual source amount, actual estimated network fee, provider, estimated payout, target network/account and refund address. Existing secure wallet authentication and TRON resource checks remain in the confirmation pipeline.

`BsvHomeTransactionCheckpoint` saves the signed raw transaction, locally computed hash, source wallet/asset/address, recipient, exact amount and original network fee in the existing Keychain adapter under `portalpayments` before broadcast. It accepts fixed transfers of native BSV, native mainnet TRX and the exact TRON USDT asset. Native TRX validation binds the unique `TransferContract`, positive exact amount, sender, recipient, JSON/protobuf bytes, hash and recovered signature owner, and rejects memos. The existing token validator remains on the USDT path. A failed secure write blocks broadcast. Stored bytes are checked against the confirmed transfer and their hash. Immediately before a broadcast, the checkpoint revalidates the active workflow, wallet, fresh order status and deposit expiry; cancellation before that gate blocks sending while keeping the saved transaction. Once an HTTP broadcast has started, cancellation cannot recall a transaction already accepted by the chain. The order-bound checkpoint rejects a different second signed transaction. Ordinary transfers without a checkpoint retain their existing behavior.

A saved transaction is not proof of broadcast. Recovery first fetches current order and chain state. A matching known payment can be reported with its original hash; a replay is allowed only for a still-payable order and uses the same signed bytes. The recovery confirmation displays the original amount and network fee, without creating a new transaction or loading a replacement fee. TRON's existing receipt endpoint can return no receipt for a pending transaction; this does not prove it is absent from the mempool. Identical-byte replay preserves the same transaction ID. An expired TRON raw transaction cannot be replaced by a newly signed payment for that order.

A genuine broadcast result is reported to Portal using the journal's hash. Reporting failure preserves the local payment and disables another payment; order refresh retries the same report. It is presented separately from a failed chain payment. App restarts retain operations, orders and signed-payment recovery state. Closing a confirmation before payment keeps the order available.

## Status, actions and settlement

Order phase, verification, synchronization and settlement are separate states. Active orders have a non-settled resolution without an age cutoff; older orders are accessible through the full paginated list. The visible order refreshes periodically, and returning to the foreground updates active orders. Stale or unknown payment details disable payment. Provider holds or KYC requirements do not imply a refund. Only the explicit refunded state is labelled refunded.

Actions are resolved through the order/action endpoint, validated as unexpired HTTPS URLs without embedded credentials, and opened using the existing Safari sheet. Returning refreshes the order; opening a page does not locally approve verification. Core binds resolution requests to the same wallet identity.

Provider completion is displayed separately from chain payout verification. `verifyPayout` requires the returned payout transaction to be confirmed and match its hash, target asset, recipient and actual returned payout amount. A provider completion without that evidence stays unverified. The document does not define a net refund amount field; refund hashes and the provider refund status can be displayed, but no independently verified refund amount is claimed without a complete actual record.

## BSV protected outputs

BSV native balance and input selection share a verified output classifier. It verifies each referenced parent output, value, confirmation and ownership; standard spendable native P2PKH outputs are eligible. One-satoshi outputs and recognized inscriptions/token co-signature scripts are excluded. The signer separately rejects one-satoshi inputs. Unknown or inconsistent outputs fail closed. This includes non-one-satoshi token outputs rather than assuming all token balances are one satoshi. Parent transaction fetching is deduplicated within a request, with additional provider calls proportional to distinct source transactions.
