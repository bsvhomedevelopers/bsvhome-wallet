Ordinary Confirm, Member multisig and independent funding-payer scopes reject cold metadata through that same actual store. Native proposal/funding/online authentication repeats the actual-wallet financial check around password access and at the key queue. Pure public identity queries remain available. This financial boundary does not claim to isolate all cryptographic operations: retained nontransaction Portal challenge/BitcoinMessage signing is outside it. The new unified app retains networking, so the signer must be disconnected manually; only the retained isolated cold composition has a rejecting provider.

## Transactions, persistence and safety

The daily device imports the public Pairing or account xPub and prepares and persists Request/Review before displaying the request QR. The cold wallet device scans the QR and independently recalculates the review from complete previous transactions. It requires an explicit check and system authentication, signs internally in Rust, verifies all signatures and persists Signed before displaying its QR. The daily device verifies the returned signature against the original request before enabling authenticated broadcast. Transfer amounts use checked integer satoshis and display full precision.

The pending store is scoped by application WalletId, uses compare-and-swap, atomic writes, complete file protection and backup exclusion after replacement. It preserves original protocol strings and broadcast state. Cached review/txid fields never establish trust: reopening recomputes them. Corruption or a different account profile blocks the operation. An unsigned request can be cancelled. Online signed requests cannot be overwritten; broadcast retries use the same signed bytes and expected transaction ID. A broadcast transport failure is accepted as recovered success only when fetching the expected raw transaction returns those exact bytes.

Once the gateway verifies broadcast success, an in-memory result is recorded before awaiting persistence. A subsequent storage failure returns `broadcasted = true` with a separate `persistence_error`; the UI retains the result and transaction ID. Reopening through the same service revalidates and overlays that result only on the identical saved request, review and signature, and retries the status write. After process restart, the durable Signed remains the retry source; retrying never constructs a replacement payment. A refresh failure after successful broadcast also leaves the success result intact.

An offline device cannot know whether its previous signature was broadcast. Starting another request therefore requires an explicit acknowledgement that the previous signature was saved or delivered and remains valid. The old Signed remains durable while the next request is reviewed; cancelling that review restores it, and a failed new-signature write preserves it. This action never claims to revoke a signed payment or confirm its chain status.

Cold checkpoints use version 2 and the protocol's `0xfffffffd` sequence; existing version-1 hot checkpoints keep their original sequence and validation. Both require full input signatures and exact spend validation. Cold pending recovery uses its own store; it does not enter an ordinary hot-signing path.

Dynamic QR uses the shared Core framing contract: 1 MiB payload, 800 Base64 characters per fragment, at most 1800 indexed frames. The existing scanner's continuous mode remains open for updates; missing frames are progress, while conflicts discard the current session. Playback advances every 700 ms and supports pause and manual frame changes. Leaving or backgrounding stops scanning and playback.

Creation, import, backup, signing and broadcast require explicit device-owner authentication. Sensitive callbacks recheck their wallet and operation context; repeated actions are rejected while busy. Background, lock, capture and exit clear temporary secrets and invalidate confirmations. Inactive scenes mask content. iOS screenshot notifications only support subsequent cleanup; this feature does not claim to prevent screenshots. Full recovery backup is temporary text with no clipboard, sharing, file export or secret QR. Secret metadata errors disable backup without hiding other wallet details or guessing a mnemonic.

Existing Keychain authentication and access controls remain enabled. On hardware, password access can require a second system prompt after the explicit action authentication; no cross-operation authentication cache weakens this policy. Physical-device prompt count and cancellation remain acceptance items.
