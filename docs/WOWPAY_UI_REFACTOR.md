## Native Flow and Navigation Boundaries

The HTML is the visual reference; its simulated one-click transfers, hardcoded rates and fake wallet completion do not replace the accepted real-wallet contract. Supported send remains recipient → amount → confirmation/authentication/signing in the existing Transfer feature. Supported receive generates an actual chain/account payload. Native BSV receive uses the current wallet's real account address; the separate deferred BSV prototype form remains unavailable. Real swap remains the existing quote/asset/network/slippage/confirmation flow, reached through a dedicated supported-swap action; prototype BSV/MNEE pairs never emit an estimated real quote.

The profile import entry now pushes welcome → method → a type-specific input page in the settings navigation path. Phrase import offers five Core-supported word counts; private-key and watch-only imports choose a supported network before input. The original onboarding import flow remains available at its existing entry points. Both inputs use the existing real import service and validation; neither inserts demo credentials or reports fabricated success. Keystore has an unavailable action. The profile menu and welcome page both push the prototype create introduction and then the real terms, reminder, backup, verification and setup steps in the settings navigation path. Onboarding and wallet-management sheet callers continue to use the same secure creation flow. Native navigation bars, sheets, list rows and system permissions remain where they own safety or reachability. Visual review covered the four main pages, BSV, the supported-swap entry and small-screen welcome. This delivery does not claim pixel parity for every state of the HTML.

`ios/BsvHome/Views/MainTabView.swift`, `ios/BsvHome/Types/TabItem.swift`, and `ios/BsvHome/Navigation/NavigationStateManager.swift` define independent home/assets/swap/profile paths. The assets path retains its `.wallet` code identity so existing asset deep links keep their owner. `ios/BsvHome/Types/WalletTabDestination.swift` owns `.activity`, `.paymail`, the import routes and `.createIntro` in the settings/profile path. Import and profile-entry creation pages hide the Tab bar and support ordinary back navigation until the created wallet reaches setup, which retains the existing back restriction after import. Creation route values contain no mnemonic or wallet payload; `CreateWalletFlow` owns temporary words in memory and discards them on exit. A completed new import presents wallet setup above the tab paths so switching the current wallet cannot remove setup when navigation resets. `ios/BsvHome/Navigation/Transactions/TransactionsNavigationView.swift` appends NFT destinations to the settings path. Settings callbacks are passed by `ios/BsvHome/Navigation/Settings/SettingsNavigationView.swift` from `MainTabView`; its direct create entry pushes the same introduction as the welcome page, Paymail opens the Core-backed management scene; address opens its unavailable scene, and activity pushes without nesting another activity sheet.

`WalletHeaderViewModel.isEnabled(_:)` in `ios/Packages/PrimitivesComponents/Sources/ViewModels/WalletHeaderViewModel.swift` projects the Core-provided actions. Home send/receive and the supported-swap action use it, preserving watch-only and other disabled states; no app-owned capability list was added. The home swap tile can still navigate to the prototype landing even when real swap is disabled.
